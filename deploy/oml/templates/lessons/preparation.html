라벨은 사람이 느낌으로 붙이는 등급이 아닙니다. 실제 기록의 명확한 조건에서 계산합니다. 이 실습의 기록은 시드가 고정된 합성 주문입니다. 생성기의 숨은 구매 성향에 무작위성을 더했으므로 정답을 완벽하게 예측할 수 있도록 만든 데이터가 아닙니다.

라벨 누수: 가장 흔한 실수

10월 구매 횟수, 10월 결제 금액, 라벨을 복사한 열을 입력으로 사용하면 미래를 이미 알고 답하게 됩니다. 모델 점수는 높아질 수 있지만 실제 10월 1일에는 그 값을 알 수 없습니다.

NO_REBUY를 붙이려면 10월 31일까지 관측이 완료되어야 합니다. 중도 탈퇴·기록 누락·데이터 수집 종료 때문에 결과를 모르는 고객을 무조건 NO_REBUY로 만들면 라벨 오류가 됩니다. 실제 과제에서는 관측 완료 조건도 명시하세요.

한 주문에 도서 두 권이 들어 있으면 주문 횟수는 1이고 결제 금액에는 두 권의 가격이 합산됩니다. OML_ORDERS의 기본키는 (ORDER_ID, BOOK_ID)입니다. 기존 마당서점 주문 테이블에 장바구니 개념을 명확하게 붙인 교육용 확장입니다.

01_schema.sql의 OML_DERIVED_FEATURES에서 기간 조건과 집계를 확인하세요. 10월 정답 계산은 과거 집계와 별도의 CTE로 구성됩니다. 그 결과를 OML_FEATURES에 저장합니다.

데이터를 먼저 의심하는 습관

  1. 중복과 단위를 검사합니다. 고객 ID 중복, 원/천원 혼용, 음수 금액, 미래 날짜를 확인합니다. 실습 업로드는 결측값을 자동으로 숨기지 않고 오류로 알려줍니다.
  2. 결측 처리 규칙을 정합니다. 실데이터에서 대체값을 쓴다면 TRAIN에서만 평균·중앙값 등을 계산하고 TEST와 새 입력에 같은 값을 적용합니다. 정답 라벨이 없는 행을 임의로 채우지 않습니다.
  3. 고객 단위로 분리합니다. 같은 고객의 여러 행이 TRAIN과 TEST에 동시에 들어가면 독립적인 평가가 아닙니다. 이 샘플은 고객당 한 행이며 라벨별 고정 해시 순서로 약 20%를 TEST에 둡니다.
  4. 분리 후 전처리합니다. 분포를 살펴보거나 변수를 고르는 데 TEST를 반복 사용하지 않습니다. 튜닝이 필요하면 TRAIN 안에서 검증셋을 추가로 나누고 마지막에 TEST를 한 번 사용합니다.
  5. 학습과 예측의 규약을 맞춥니다. 열 이름·단위·관측기간이 같아야 합니다. PREP_AUTO는 알고리즘의 자동 준비 기능이며, 잘못된 라벨이나 시간 누수까지 해결하지 않습니다.

실습의 무작위 고객 분리는 같은 기간의 새로운 고객에 대한 연습입니다. 다음 달 성능을 주장하려면 여러 기준월을 구성한 시간 순서 평가도 필요합니다. 작은 합성 데이터만으로 계절성이나 실제 운영 환경을 검증할 수 없습니다.

업로드 전에 확인할 CSV 규약

customer_id,order_count,total_amount,recency_days,category_count,label,split

UTF-8 CSV, 30~1,000행, 최대 2MB입니다. 샘플은 120행입니다. 두 라벨은 각 TRAIN/TEST에 최소 3행씩 있어야 합니다. 파일 전체를 검증한 뒤에만 현재 실습 데이터를 교체합니다. 실제 개인정보는 입력하지 마세요.

실습실의 검증·미리보기에서 행 수와 라벨 분포를 확인하고 검증한 데이터 적용을 누릅니다. 데이터가 바뀌면 이전 분류모델의 예측을 차단하여 다른 데이터의 결과를 혼동하지 않도록 합니다. 원본 주문·연관규칙 데이터는 CSV 업로드로 바뀌지 않습니다.
